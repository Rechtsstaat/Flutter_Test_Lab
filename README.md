# Flutter_Test_Lab

한 번 입력한 표준 매물 데이터를 **당근·다방·직방**의 매물 등록 폼에 함께 반영하는 것을 목표로 하는 Flutter 실험 프로젝트입니다.

## 프로젝트 목표

플랫폼마다 같은 매물 정보를 반복 입력하는 불편을 줄이기 위해, 공통 데이터 모델과 하나의 통합 입력 화면을 만들고 각 플랫폼의 공식 연동 방식 또는 사용자 승인을 거친 입력 흐름으로 연결하는 것이 최종 목표입니다.

목표 흐름은 다음과 같습니다.

1. 사용자가 앱에서 표준 매물 정보를 한 번 입력합니다.
2. 앱이 당근·다방·직방에 필요한 필드로 데이터를 변환합니다.
3. 사용자가 내용을 확인하고 승인합니다.
4. 각 플랫폼의 지원 범위에 따라 공식 API 연동 또는 폼 입력 보조를 수행합니다.

## 플랫폼을 켜고 끄는 스위치

**지금 당근은 잠시 내려 뒀습니다** — 매물 내리기(거래완료·미노출) 자리를 아직 수집하지 못해서입니다.
화면에는 회색 「준비 중」 카드로 남아 있고 고를 수 없으며, 등록·종료 흐름에도 들어가지 않습니다.
당근용 어댑터·사진·주소 코드는 **그대로 남겨 뒀습니다.**

켜고 끄는 곳은 `lib/fields.dart` 의 `ListingPlatform.status` **한 줄**입니다.

```dart
ListingPlatform.daangn => PlatformStatus.paused,   // live 로 바꾸면 되살아납니다
```

화면과 흐름은 `livePlatforms` 와 `isLive` 만 보므로 따라옵니다.

**플랫폼을 하나 더 붙일 때**는 `ListingPlatform` 에 값을 더하면 됩니다. 설정이 전부
`switch` 로 적혀 있어 **컴파일러가 채워야 할 곳(주소·버튼 이름·로그인 확인법·색·어댑터)을
하나씩 짚어 줍니다.** 마지막으로 `status` 를 `live` 로 두면 화면·흐름에 저절로 들어옵니다.

## 현재 상태: 실물 직방·다방에 붙는 폼 주입 프로토타입

앱은 이제 **실제 직방 CEO(`ceo.zigbang.com`)와 다방프로(`pro.dabangapp.com`)** 에 붙습니다. 통합 폼의 값을 앱 내부 WebView에 띄운 각 플랫폼의 실제 매물 등록 폼에 주입하고, 입력 결과와 플랫폼이 받지 못한 항목의 사유를 보여 줍니다. 등록 버튼은 여전히 사람이 누르므로, 누르면 매물이 **실제 사이트에 등록**됩니다.

### 실물과 미러

주소는 `lib/fields.dart` 의 `ListingPlatform.urlsOn(PlatformSite)` 한 표에 있습니다.

| | 실물 (기본) | 미러 |
|---|---|---|
| 직방 매물 등록 | `ceo.zigbang.com/ads/oneroom/ad-item/new` | `/zigbang/form/oneroom/` |
| 직방 광고 목록 | `ceo.zigbang.com/ads/oneroom?status=open` | `/zigbang/ads/oneroom/?status=open` |
| 직방 로그인 | `ceo.zigbang.com/account/login/email` → `account.zigbang.com` OAuth | `/zigbang/account/login/email/` |
| 다방 매물 등록 | `pro.dabangapp.com/form/room` | `/dabang/form/room/` |
| 다방 광고 목록 | `pro.dabangapp.com/room/dabang-list/public` | `/dabang/room/dabang-list/public/` |
| 다방 로그인 | `pro.dabangapp.com/login` | `/dabang/login/` |

실물 경로는 2026-09-20 에 직방 CEO 의 Next.js 라우트 표와 다방프로의 react-router 번들, 그리고 로그인 안 된 요청의 실제 응답으로 확인했습니다. 실물과 미러가 다른 점은 다음과 같고, 앱은 둘 다 다룹니다.

- **직방 로그인은 도메인을 건너갑니다.** 로그인 안 된 요청은 307 로 `/intro` 랜딩에 가고, 로그인은 `account.zigbang.com` 에서 받은 뒤 `/OAuth/Callback` 이 `ceo_zauth` 를 심고 돌아옵니다. 그래서 「로그인 안 됨」은 경로뿐 아니라 호스트로도 가립니다.
- **다방프로는 한 장짜리 앱(SPA)입니다.** 로그인 안 된 `/dashboard` · `/form/room` · 광고 목록은 200 으로 껍데기를 준 뒤 랜딩 `/` 으로 **주소만** 바꿉니다. 페이지 로드가 없으므로 WebView 의 URL 변경(`onUrlChange`)으로 듣습니다. 로그인을 마치고 대시보드로 가는 것도 같은 식이라 연동 확인도 거기서 다시 합니다.
- **다방 `login/check` 의 답 모양이 다릅니다.** 실물은 `{"code":200,"result":false}`, 미러는 `{"isLogin":false}` 입니다. 둘 다 읽습니다.
- 연동(0011)이 로그인 화면이 아니라 **랜딩**(직방 `/intro`, 다방 `/`)에 떨어지면 한 번만 플랫폼 로그인 화면으로 넘겨 줍니다.
- 실물 폼은 페이지 로드가 끝난 뒤 그려지므로, 어댑터는 폼의 입력란이 나타날 때까지(최대 20초) 기다렸다가 돕니다. 끝내 나타나지 않으면 「등록 폼의 입력란을 찾지 못했어요」를 확인할 항목에 올립니다.
- 어댑터는 미러가 덧붙인 `data-mirror*` 표식에 기대지 않고, 실물 페이지 자체의 `name`·섹션 id·줄 제목·ARIA 역할로 칸을 찾습니다.

**미러로 돌리려면** 빌드할 때 `--dart-define=PLATFORM_SITE=mirror` 를 줍니다. 계정 없이 어댑터를 재 보거나 통합 테스트를 돌릴 때 씁니다. 헤드리스 크롬 하네스(`test/mirror_browser_test.dart`)는 늘 미러를 잽니다.

```bash
flutter run --dart-define=PLATFORM_SITE=mirror
```

### 다방은 주소를 고르면 폼을 되돌린다 (실물 실측 2026-09-20)

실물 다방프로에서 **주소를 확정하는 순간 폼이 처음 상태로 돌아갑니다.** 주소와 섹션이 다른 「제목」(`detail_info`)에 손으로 친 글자까지 사라집니다. 미러에는 없는 성질이라 계정 없이는 보이지 않았습니다.

예전 어댑터는 카카오 주소 화면을 **맨 마지막**에 띄웠습니다(전체 화면 겹이 다른 입력을 가리므로). 그래서 43건을 넣고 41건을 되읽어 확인한 직후 주소가 확정되면서 **그 43건이 전부 날아갔고**, 사람 눈에는 주소와 동·호만 남았습니다. 「입력 43건 · 검증 41건」은 거짓이 아니라 **철 지난 숫자**였습니다.

두 가지로 고쳤습니다.

- **주소를 앞으로 당겼습니다.** 매물유형(①) 다음이 곧 주소(②)이고, 거기서 카카오 화면을 띄워 주소가 앉을 때까지(동·호 칸이 풀릴 때까지, 최대 60초) 기다린 뒤 나머지를 채웁니다. 되돌리는 쪽을 먼저 지나가면 뒤의 값이 살아남습니다. 사람이 끝내 고르지 않아도 멈추지 않고 나머지를 채웁니다.
- **끝에서 한 번 더 대조합니다**(`reconcile`). 성공한 조작마다 「다시 재는 법·다시 넣는 법」을 적어 두었다가, 마지막에 전부 다시 읽고 없어진 것을 다시 넣습니다. 다시 넣는 일이 또 다른 행을 되돌릴 수 있어(매물유형을 다시 고르면 7행이 다시 그려집니다) 잠잠해질 때까지 최대 세 바퀴 돕니다. 늦게 도착한 주소도 `watchAddress` 가 듣고 대조를 한 번 더 부릅니다. **「검증」 숫자도 여기서 본 것으로 고쳐 적습니다** — 넣던 순간의 숫자는 사람에게 거짓말이 됩니다.

값을 받고 닫히는 창(월 관리비 상세입력) 안의 칸은 적어 두지 않습니다. 닫히면 사라지는 것이 정상이라, 적어 두면 「사라졌다」는 오탐이 됩니다.

미러에 실제로 돌려 옛 어댑터와 견줬습니다 — `applied 40 · verified 39 · missing 0`, 폼 최종 상태까지 동일합니다(`--job=inject`).

**사용승인일은 폼이 형식을 고칩니다.** 실물은 넣은 `20250301` 을 제 형식으로 되돌려 주어, 글자 그대로 견주면 넣고도 실패로 읽혔습니다. 그 칸만 **숫자만 같으면 같은 값**으로 봅니다(`sameDigits`) — 느슨한 비교를 전부에 주면 진짜 실패가 묻힙니다. 그리고 값이 어긋났을 때는 폼이 **무엇으로 읽었는지**를 함께 적습니다. 「같은 값을 못 읽었다」만으로는 형식을 고친 것인지 값을 버린 것인지 알 수 없어, 실물에서 한 번 더 재 봐야 했습니다.

### 사진은 폼이 다 채워진 **뒤에** 붙인다 (실기기 실측 2026-09-20)

사진 첨부가 실기기에서 「현재 0장입니다」로 끝나던 것은 **업로드 문제가 아니라 순서 문제**였습니다. 실물에서 재 본 어댑터 쪽 가정은 전부 맞았습니다 — 카드를 찾는 규칙(`section#visual_info [class*="SortableContainer"] [data-index]`)도, 앱이 고르는 입력란(`multiple && accept === 'image/*'`)도, `DataTransfer` + `input`·`change` 로 넣는 방식도 실물 크롬에서 1초 만에 카드를 만들었습니다 (`test/tools/dabang_photo_probe.js`, `…_attach_probe.js`).

실기기가 마지막에 들고 온 증거가 답이었습니다: 파일은 정상으로 되읽혔고, **서버 id(`data-id`)까지 받은 카드가 생겼다가 사라졌고**, 사진 자리 노드가 통째로 갈려 관찰자는 그 자리에서 멈췄습니다. 업로드는 성공했고 그 뒤에 **폼이 사진을 쓸어 간 것**입니다.

쓸어 간 것은 우리 자신이었습니다. `WebViewController.runJavaScript` 는 async 어댑터의 **첫 await 에서 돌아오므로**, 사진 첨부가 폼 입력과 나란히 돌았습니다. 그리고 바로 위에 적은 대로 **다방은 주소를 고르는 순간 폼을 처음 상태로 되돌립니다.** 값은 `reconcile` 이 다시 넣지만 **사진은 아무도 다시 붙여 주지 않습니다.**

- **순서를 나눴습니다.** 세 어댑터가 끝날 때 `window.__flrFormDone` 을 세우고, `awaitFormAdapter` 가 그 표식을 기다린 뒤에야 사진을 붙입니다(최대 3분, 끝내 말이 없으면 붙여 봅니다). 그래서 사진이 붙는 시점이 예전보다 늦게 보이는 것이 정상입니다.
- **붙이는 동안 폼을 잠급니다.** 사진 다리가 `until` 을 앞으로 밀고, 어댑터의 되돌림 감시자는 그동안 `reconcile` 을 돌리지 않으며 사진 자리 안에서만 난 변화는 무시합니다 — 막지 않으면 **사진 카드가 생기는 것 자체가** `reconcile` 을 불러 매물유형을 다시 누르고, 그게 방금 붙인 사진을 지웁니다.
- **쓸려 간 것을 알아보고 다시 붙입니다.** 사진 자리 노드의 정체(`remade`)와 카드의 소멸(`gone`)을 따로 재고 둘이 겹칠 때만(`wiped`) 남은 예산을 흘려보내지 않고 한 번 더 붙입니다. **카드를 안고 다시 그려진 경우는 다시 붙이지 않습니다** — 그러면 남의 광고에 같은 사진이 두 장 붙습니다.
- **잠긴 카드도 인정합니다.** 실물은 서버 id 를 받은 카드를 `aria-disabled=true` 로 둔 채 두기도 합니다. `aria-disabled === 'false'` 만 고집하면 **이미 올라간 사진을 실패라고 말하게 되므로**, 새 카드가 제 id 를 달고 4초를 버티면 붙은 것으로 봅니다. 성공을 지어내는 것이 아니라 플랫폼이 만들어 놓고 치우지 않은 카드를 인정하는 것입니다.

기다리는 시간은 사진 크기를 따라 늘어나고(`settleBudget`: 기본 45초 + MB당 20초, 120초에서 멈춤), 시간이 다하면 본 것을 그대로 적습니다 — 기다린 초, 사진 크기, 플랫폼이 화면에 띄운 말, 페이지가 낸 오류. 오류는 **엿듣기만** 합니다(`error`·`unhandledrejection` 리스너). `fetch`·`XHR` 을 바꿔 끼우면 더 볼 수 있지만 하지 않습니다 — 남의 계정으로 도는 실물 등록 폼이라, 래퍼가 잘못되는 순간 그 사람의 업로드가 깨집니다.

브리지는 미러에서 실제로 구동해 확인했고(`--job=bridge`), **판단 규칙은 `test/tools/photo_bridge_probe.mjs` 가 가짜 DOM 과 우리가 쥔 시계 위에서 그대로 돌려 봅니다** — 글자 검사로는 「카드가 앉았는가·폼이 다시 그려졌는가·떴다 사라졌는가」를 믿을 수 없고, 47초를 헛기다리게 만든 것이 바로 그 판단이었기 때문입니다.

**아직 실기기에서 확정하지 못한 것** — 폼을 되돌린 것이 주소 선택인지 그 밖의 무엇인지는 가리지 못했습니다. 이제 실패하면 메시지에 「사진 자리가 통째로 다시 그려졌습니다」가 찍히므로 다음 실측에서 드러납니다.

### 실물 계정으로 재 볼 때 — 빗장과 탐침

실물 계정은 **남의 영업 자산**입니다. 되돌릴 수 없는 일은 「등록 완료」와 「광고 종료」 두 번의 누름뿐이고, 등록은 이미 사람 몫이라 남은 건 종료입니다. 재 보는 동안은 빗장을 걸어 두세요.

```bash
flutter run --dart-define=GUARD_LIVE_ADS=1
```

빗장이 걸리면 **광고 목록(2022 「등록된 광고 보기」)과 광고 종료(102 「광고를 종료할래요」 → 301·3021)로 가는 길이 화면에서 사라집니다.** 102 에는 왜 없는지가 대신 적힙니다. 등록 폼 입력은 그대로 돌아갑니다. 스위치는 `lib/fields.dart` 의 `guardLiveAds` 한 곳입니다.

입력이 빗나갈 때는 **계정을 넘기지 말고 폼의 구조만 떠 오세요.** 다방 어댑터는 `#room_info`·`#trade_info` 섹션 id 와 `th` 줄 제목, `td` 안의 `header`·`label` 글자로 칸을 찾는데(`dabangInjectionScript`), 이 기준은 전부 **미러를 떠서** 쓴 것이라 실물이 다르면 입력이 통째로 빗나갑니다. 무엇이 다른지는 값이 아니라 구조만 보면 압니다.

1. 계정 주인이 크롬에서 `pro.dabangapp.com` 에 로그인하고 `/form/room` 을 엽니다.
2. DevTools 콘솔에 `test/tools/dabang_form_probe.js` 를 통째로 붙여넣고, `copy(__dabangProbe)` 로 결과를 담습니다.
3. 그 결과를 기준선 `test/tools/dabang_form_probe.mirror.json` 과 견줍니다.

### 화면 흐름

`02_하이파이` 의 overview 프레임이 정한 흐름을 따릅니다. 8단계로 나눈 등록 폼 변형은 파일에 「이거 보지 마세요」로 표시돼 있어 반영하지 않았습니다.

| 흐름 | 화면 |
|---|---|
| 최초 진입 | 000 스플래시(점 세 개가 합쳐지는 모션, 약 2.5초 뒤 220ms 디졸브) → 001 플랫폼 연동 선택 → 0011 플랫폼별 로그인 웹뷰 → 002 연동 완료 → 101 홈 |
| 광고 등록 | 101 → 201 광고 입력 폼 → 202·203 광고 입력(Process Hub) → 204 등록 완료 |
| 예외 | 205 확인 필요 → 2051 확인하기-웹뷰 / 206 시스템 오류 → 2061 재시도 → 2062 일부 성공 |
| 광고 종료 | 101 → 102 매물상세 → 301·302 플랫폼 선택 바텀시트 → 3021 광고 종료-웹뷰 → 303 종료 완료 |

상태 색은 overview 의 약속 그대로입니다 — 등록 완료·광고 중 `status/success`, 입력 중 `action/primary`, 입력 대기·미등록 `text/disabled`, 확인 필요 `status/warning`, 연결 오류 `status/error`.

### 네이티브 안의 웹뷰

등록하는 동안 화면은 계속 한방이 쥐고 있고, 플랫폼 페이지는 그 아래에서 돌아갑니다(`lib/mirror_session.dart`, `lib/screens/publish_flow_page.dart`).

- 플랫폼마다 `MirrorSession` 이 WebView 를 하나 갖고 페이지 로드·어댑터 실행·사진 첨부를 맡습니다. WebView 는 흐름이 끝날 때까지 **항상 화면 트리에 붙어 있고**(창에서 떨어진 WKWebView 는 타이머가 느려집니다), 허브가 그 위를 덮고 있다가 필요할 때 걷힙니다.
- 「입력 과정 보기」를 누르면 허브가 내려가고 입력되는 모습이 그대로 보입니다(2021, 「입력이 끝날 때 까지 잠시만 기다려주세요」 토스트).
- 어댑터가 끝나면 한방이 스스로 페이지를 올리고 「입력이 끝났어요 / 등록하기 버튼을 직접 눌러주세요」를 띄웁니다(2023). **플랫폼의 등록 버튼은 사람이 누릅니다.** 한방은 페이지에 넣어 둔 감시 스크립트로 그 누름(`isTrusted` 인 클릭만)을 듣고 다음 플랫폼으로 넘어갑니다. 버튼 이름은 미러 저장소 기준 직방 「매물 등록 완료」, 다방 「등록 완료」, 당근 「매물 등록하기」입니다.
- 등록을 누르지 않고 돌아오면 그 플랫폼은 「확인이 필요해요」(205)가 되고 다음 플랫폼이 시작됩니다. 「확인하기」는 채워 둔 그 페이지를 다시 올립니다(2051). 어댑터가 채우지 못한 항목은 페이지 오른쪽 위 「확인할 항목 / 참고 사항」 칩에서 볼 수 있습니다.
- 페이지가 뜨지 않거나 3분 안에 입력이 끝나지 않으면 「연결이 어려워요 · 다시시도」(206), 한 번 더 실패하면 「나중에 다시 시도해주세요」(2062)입니다.
- 「등록된 광고 보기」(2022)와 광고 종료(3021)는 각 미러의 광고 관리 화면을 엽니다. 종료는 직방 「매물 종료하기」, 다방 「광고 종료」를 누르면 감지합니다. 당근 미러에는 아직 종료 버튼이 수집되지 않아, 뒤로 가기에서 「그대로 두기」를 고르면 광고를 유지한 채 넘어갑니다.
- 0011 은 **각 플랫폼의 로그인 화면을 그대로** 띄웁니다. 앱은 로그인 화면을 따로 부르지 않고 대시보드 주소만 열고, 로그인이 안 돼 있으면 플랫폼이 알아서 되돌려 보냅니다. 한방은 입력값을 보지 않습니다 — 아이디와 비밀번호는 플랫폼 자신의 폼에서 플랫폼 자신의 엔드포인트로 가고, 세션은 플랫폼만 읽을 수 있는 WebView 쿠키 저장소에 남습니다.
  - 연동됐는지는 「제출했다」가 아니라 **세션이 생겼는가**로 가릅니다. 확인법은 플랫폼마다 다릅니다 — 직방 `ceo_zauth` 는 페이지가 심고 HttpOnly 가 아니라 `document.cookie` 로 보이고, 다방 `auth_key` 는 서버가 심은 HttpOnly 라 보이지 않아 플랫폼에 `login/check` 로 묻습니다. 무엇을 보고 판단했는지는 연동 뱃지에 적힙니다.
  - 미러는 직방 `/zigbang/account/login/email/`, 다방 `/dabang/login/` 이 로그인 화면이고 (`mirror@test.kr` / `mirror`), 당근 미러에는 로그인이 없어 중개소 홈이 곧 시작점입니다.
  - 예전에는 한방이 만든 **임시 로그인 화면**을 띄웠습니다. 미러가 로그인 뒤 화면부터 수집돼 있다는 전제였는데, 그 뒤 미러가 로그인 앞단까지 수집하면서 직방·다방의 **모든** 페이지를 로그인 뒤로 가뒀습니다. 임시 화면은 세션을 만들지 않으니 미러가 이후 요청을 전부 302 로 되돌렸고, 그 결과 연동은 「완료」라고 표시되는데 매물 등록은 3분 타임아웃이 끝날 때까지 미러의 첫 화면만 붙들고 있었습니다.
- 플랫폼이 로그인 화면으로 되돌려 보내면 기다리지 않고 바로 「로그인이 풀렸어요」로 끝냅니다 — 요청한 자리에 못 닿았다는 것이 곧 신호입니다.

### 주소 검색

직방·다방 미러는 주소를 카카오 우편번호 서비스로 받습니다(당근은 아래 「당근 미러」 참고). 카카오의 `Postcode.open()` 은 `window.open()` 으로 별도 창을 띄우는데, WKWebView 에는 팝업 창이 없어 그 요청이 같은 웹 뷰에 실리면서 미러 폼이 빈 화면으로 덮였습니다. 지금은 `daum.Postcode` 를 감싸 두고 `open()` 요청을 **같은 인스턴스의 `embed()`** 로 바꿔, 페이지 안에 세운 전체 화면 겹에 그립니다. 미러가 넘긴 `oncomplete` 를 그대로 살려 두므로 주소를 고른 뒤의 흐름(다방의 동·호 활성화와 건축물대장 창, 직방의 주소 칸 채움과 소재지 공개 확인 창)이 원래대로 이어집니다. 기기의 뒤로 가기는 이 겹을 먼저 닫습니다.

검색 결과 선택까지 자동입니다. 카카오 결과 목록은 `postcode.map.kakao.com` 에서 온 **교차 출처 iframe** 안에 있어, 미러 페이지에서 실행하는 스크립트로는 읽을 수도 누를 수도 없습니다(`WebViewController.runJavaScript` 는 최상위 프레임만 닿습니다). 그래서 **그 프레임 안에서** 도는 스크립트를 플랫폼마다 네이티브로 넣습니다.

- **iOS**: WKWebView 의 `WKUserScript(forMainFrameOnly: false)` 를 씁니다. webview_flutter 가 `WKWebViewConfiguration` 을 밖으로 내주지 않으므로, 플러그인이 JavaScript 채널을 등록할 때 쓰는 `addScriptMessageHandler:name:` 을 바꿔 끼워 같은 content controller 를 잡습니다 (`ios/Runner/FrameScriptBridge.swift`).
- **Android**: AndroidX WebKit 의 `WebViewCompat.addDocumentStartJavaScript` 를 씁니다. Dart 쪽이 `AndroidWebViewController.webViewIdentifier` 를 넘기면 `WebViewFlutterAndroidExternalApi.getWebView` 로 그 WebView 를 찾아, 카카오 출처(`kakaoPostcodeOrigins`)의 프레임에만 스크립트를 넣습니다 (`android/app/src/main/kotlin/.../FrameScriptBridge.kt`). 문서가 시작될 때 들어가므로 스크립트는 `DOMContentLoaded` 까지 기다렸다가 돕니다.

프레임 안 스크립트는 카카오가 각 후보에 붙여 둔 한글 주소(`span.txt_address[data-addr]`)를 통합 폼 주소와 견줍니다. 시·도 축약형(`서울` ↔ `서울특별시`)을 맞추고 괄호 안 건물명을 뺀 뒤, 앞에서부터 겹치는 길이와 번지 일치 여부로 점수를 매겨 가장 높은 후보를 누릅니다. 점수가 같거나 판단 근거가 없으면 카카오가 관련도 순으로 준 **맨 위 항목**을 고릅니다. 도로명 하나에 지번이 여럿이면 뒤따르는 지번 선택 화면도 같은 기준으로 한 번 더 고릅니다.

자동 선택은 **앱이 넣은 검색어 그대로일 때 한 번만** 동작합니다. 사용자가 검색창을 고쳐 다른 곳을 찾으면 그 선택은 건드리지 않습니다. 자동 선택이 되지 않는 환경(문서 시작 스크립트를 지원하지 않는 오래된 Android System WebView 등)에서는 화면이 그대로 떠 있어 직접 고르면 되고, 결과 화면 상태줄에 `주소 자동 선택` 표시로 어느 쪽인지 알려 줍니다.

다방의 건축물대장 자동 조회 창은 이미 입력한 면적·용도·승인일이 공공데이터 값으로 덮어써지지 않도록 「직접 입력」으로 닫고 그 사실을 제한 사유에 남깁니다.

### 당근 미러

당근 미러(`/daangn/form/article/`)는 SEED 디자인 시스템 화면이라 줄 이름(굵은 글씨)으로 칸을 찾고, 체크 상태는 라벨의 `data-checked` 로 확인합니다. 대출·반려동물·주차 라디오는 세 줄이 같은 `name` 을 써서 `input.checked` 를 믿을 수 없기 때문입니다.

- **주소**: 카카오가 아니라 같은 출처의 주소 검색(`/api/juso`)을 씁니다. 어댑터가 「매물 주소」 창에 주소를 넣고, 결과 중 통합 폼 주소와 가장 잘 맞는 줄을 골라 상세 주소에 `101동 202호`(단일동이면 `202호`)를 넣고 「입력하기」를 누릅니다. 주소 검색 중계에 닿지 못해 예시 주소가 뜨면 고르지 않고 사유를 남깁니다.
- **건축물대장**: 「입력하기」 뒤 당근은 건축물 용도·사용승인일·전체 층·엘리베이터를 공공데이터로 채웁니다. 그래서 주소를 가장 먼저 넣고 나머지 값을 그 뒤에 넣으며, 끝에서 한 번 더 대조해 통합 폼 값으로 맞춥니다.
- **변환 규칙**: 복층형 원룸 → 오픈형 원룸 + 매물 특징 「복층」, 옥탑 → 매물 특징 「옥탑」, 단기 매물(월세·전세) → 「단기」도 함께 체크하고 금액 복사, 관리비 10만원 미만 → 「10만원 미만」 체크 + 총 관리비, 10만원 이상 → 항목별 쓴 만큼/정액만 선택(공용·정액 금액은 비워 두고 안내), 관리비 없음 → 10만원 미만 + 0만원, 아파트의 층수 비공개 → 전체 층 대비 비율로 저층·중층·고층.
- 통합 폼에 대응 값이 없는 항목(테라스·CCTV 등 옵션, 단기 조건, 공용 관리비 금액 등)은 채우지 않고 「직접 확인할 항목」에 사유를 남깁니다. 「임시저장」·「매물 등록하기」는 누르지 않습니다.

현재 포함되지 않은 범위:

- 실물 계정으로 로그인한 뒤의 화면 검증 (위 「아직 실물에서 확인하지 못한 것」)
- 당근의 실물 연결 — 실물 중개사 화면을 수집하지 못해 내려 둔 상태이고, 주소는 미러를 가리킵니다
- 플랫폼 공식 API 연동, 직방 사진 자동 업로드, CAPTCHA 처리
- 다방 건축물대장 조회 결과의 자동 선택·적용 및 비목별 관리비 금액 변환
- 운영 환경의 장애 복구 및 등록 결과 동기화

상세한 공통 필드와 플랫폼별 대응 방향은 [부동산3사 통합 기능명세서](./부동산3사_통합_기능명세서.md)를 참고하세요.

**통합 폼에 칸이 없어 못 채우는 항목**은 [다방이 통합 폼에 요구하는 것](./다방_통합폼_요구사항.md)에 따로 정리해 뒀습니다 — 실물 실측 기준이며, 통합 폼은 직방·당근까지 함께 볼 때 한꺼번에 손보기로 했습니다.

## 실행 방법

Flutter SDK와 iOS 실행 시 Xcode/CocoaPods를 준비한 뒤, 저장소 루트에서 다음 명령을 실행합니다.

```bash
flutter pub get
flutter devices
flutter run
```

특정 기기를 지정하려면 다음과 같이 실행합니다.

```bash
flutter run -d '<기기 ID>'
```

iOS 실기기에서 처음 실행할 때는 `ios/Runner.xcworkspace`를 Xcode로 열고 Runner 타깃의 Team과 고유한 Bundle Identifier를 설정해야 할 수 있습니다.

## 검사 및 테스트

저장소 루트에서 다음 명령을 실행합니다.

```bash
flutter analyze
flutter test
```

실제 미러에 붙는 WKWebView 통합 테스트는 iOS 시뮬레이터에서 실행합니다.

```bash
flutter test integration_test/daangn_form_injection_test.dart -d '<시뮬레이터 ID>'
```

```bash
flutter test integration_test/dabang_photo_upload_test.dart -d '<시뮬레이터 ID>'
```

## 실제 서비스 적용 전 확인 사항

이 프로젝트는 연구용 프로토타입이며 현재 실제 서비스에 매물을 등록하지 않습니다. 실제 연동을 구현하기 전에는 각 플랫폼이 제공하는 공식 API나 제휴 수단을 우선 확인하고, 이용약관과 자동화 정책을 준수해야 합니다. 또한 매물·계정·연락처·사진 등 개인정보의 수집 및 보관 범위, 전송 전 사용자 확인과 명시적 승인, 인증정보 보호, 오류 발생 시 복구와 중복 등록 방지 절차를 함께 설계해야 합니다.
